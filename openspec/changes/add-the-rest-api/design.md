## Context

D8 of `design-the-link-emulator/design.md` describes the server: one process, three faces, one
token, listening on the control address. This change builds the REST face; the web UI and the
MCP are changes of their own, both clients of it.

## Goals / Non-Goals

**Goals:** the routes, the account (R6, which replaced the first version's token), the ticket, the errors, the lease driving the dead-man, a
slow tick, `wanpire serve`.

**Non-Goals:** the web UI's pages; the MCP; scenarios; changing the adapter mapping through the
API (it needs the lease and a careful teardown; later); the systemd unit (the install, B4).

## Decisions

### R1. An application factory with its parts passed in

`create_app(engine, broker, config, token, list_adapters)` builds the app. The server wires the
real engine (outbound's control adapter refused, D1), a broker whose `on_clear` clears the
outbound adapter, the loaded configuration and the token file. The tests pass a recording
engine and a broker with a fake clock. Plain (non-async) route functions: FastAPI runs them in a
thread pool, and the broker holds its lock.

### R2. The ticket in a header, errors as JSON

`X-Wanpire-Ticket` carries the ticket on every call that needs one, so a route's body is only
about the link. Errors are `{"error": "<sentence>"}`:

| Status | When |
|---|---|
| 401 | no credentials, or wrong ones (R6) |
| 403 | the box has no account yet (R6) |
| 404 | an unknown ticket (expired from the queue, never issued) |
| 409 | a change by a ticket that does not hold the lease (names the holder) |
| 410 | the ticket's lease ended without it (expired, or ended by hand, with why), said once |
| 422 | an invalid link, preset or end |
| 500 | the engine failed (the `tc` error is in the sentence) |

Not taken: the ticket as the credential (it would replace the account, which every route
needs). A cookie is a browser's alone (R6); agents send Basic and keep none.

### R3. The lease drives the dead-man

`PUT link` applies with `lifetime_s = lease TTL`; a poll by the holder renews the dead-man for
the same TTL when a link is applied. A holder that keeps polling keeps its link; one that stops
loses its lease and its link on the same schedule, the engine's dead-man firing even if the
server has died.

### R4. A slow tick

A background task calls `broker.status()` every 5 s, so an expired lease is cleared and passed
on without waiting for someone to call.

### R5. `wanpire serve`

uvicorn, one worker (the broker is in memory), on the control adapter's IPv4 address, read with
`ip -j -4 addr show dev <control>`; `--host` overrides it (for a test bed). It starts without an
account, and logs that one is to be made (R6).

Not taken: listening on all addresses (D8: control only).

### R6. One account, made on the first visit (revised, the owner, 2026-10-11)

The first version had one bearer token, generated by the install into `/etc/wanpire/token`,
given to the web page and to every agent. The owner asked for a home router's way instead: the
box ships with no credentials, the first visit to its web page makes the account, a user name
and a password, and from then on everyone uses it, people and agents alike.

- **Kept** in `/etc/wanpire/account`, mode 0600: JSON with the user name, a random 16-byte salt
  and the password's scrypt hash (`n=2^14, r=8, p=1`, Python's `hashlib`, nothing to install).
  The server reads the file again when it changes (its modification time), so `wanpire account`
  run beside a live server takes effect on the next call.
- **The first visit.** With no account, `GET setup` says so without credentials, `POST setup`
  makes it once and signs the browser in, and every other route answers 403: an unset box is
  unusable, not open. Afterwards `POST setup` answers 409.
- **Agents** send HTTP Basic credentials with every call, which every HTTP client and the MCP's
  `httpx` do without code of their own, and which keeps the API stateless for them as the token
  did. A verified pair is remembered in memory as a SHA-256 of the pair, so the scrypt cost (tens of
  milliseconds on a Pi) is paid once per password, not once per poll.
- **Browsers** sign in once (`POST session`) and get a random session id in an `HttpOnly`,
  `SameSite=Strict` cookie. Sessions are in memory: a restart signs browsers out, as it ends
  leases. `SameSite=Strict` keeps another site's page from riding the cookie, and the page holds
  no secret a script could read, which the token in `localStorage` was.
- **The MCP on the box** calls the REST routes in process; it carries a random credential made at
  start and never written down, accepted only in place of Basic. The `/mcp` route itself takes
  Basic, like the API.
- **A forgotten password** is the router's reset button: `wanpire account reset` on the box
  removes the account, and the next visit makes it again. `wanpire account set <user>` sets it
  from standard input, for an install that should not wait for a visit.
- **Wrong credentials** are answered after half a second, which slows guessing down by a few
  orders of magnitude without a lockout that a stranger could use to lock the owner out.

Not taken: keeping the token for agents beside the password for people (the owner chose one
account for everyone); several accounts or roles (the broker's `who` already tells clients apart,
and a box on a bench has one owner); a default password printed on a label (a box that ships
open
until someone changes it is the router habit worth not copying); JWTs (a signed token is a second
secret to manage, and a box with one process needs no stateless sessions).

## Risks / Trade-offs

- **One worker** is one process for the web UI, the API and the MCP. → They are idle between
  calls; the work is the kernel's.
- **Plain HTTP on the control network.** → The password crosses it in clear, in Basic and when
  signing in; the README says the control network should be trusted, and a reverse proxy can
  add TLS.
- **Whoever visits first makes the account.** → Between the install and the owner's first visit,
  anyone on the control network could claim the box. The install can set the account itself
  (`--user`, the password from standard input), and the README says to visit right after
  installing.
